# PV1 UI component library

PV1 provides reusable UXML templates under `UXML/`, shared component styles in `USS/TANComponents.uss`, controllers and view models in `Scripts/`, and shared foundations under `Foundations/`.

## Unity setup

After Unity imports the files, use **Thief & the Necklace → Visual → Create PV1 Foundation Assets** to create the editable theme, color palette, and art database assets. Adjust the theme assets, then use **Thief & the Necklace → Visual → Sync Theme To Runtime Stylesheet** to regenerate the `:root` variables consumed by the shared USS. Use **Thief & the Necklace → Visual → Component Lab** to preview button variants, cards, panels, player states, timers, scores, chat and feedback; resize the window and toggle high contrast and large text there.

UXML owns component hierarchy, USS consumes shared semantic tokens, and C# binds view models and presentation events. The controllers accept strings, sprites, scores and public status only. They do not read core player/game objects or decide roles, votes, scores, or outcomes. The `RoleVisualDatabase` returns no normal-role entry for `Thief`; its separate objective/reveal sprite must only be requested by reveal presentation.

`VisualElementPool<T>` is intended for frequently rebuilt chat rows and cards. Supply a reset callback to clear bound text and state before reuse. `VisualEventBus` carries presentation notifications; gameplay event ownership remains with the core runtime.

The component lab is an Editor window, so it requires the Unity Editor. No final game screens or production illustration assets are included in PV1.

# PV2 screen production layer

PV2 assembles the PV1 components into runtime UI Toolkit screens. `Screens/` contains one UXML page for each primary `ScreenId`; `Overlays/` contains independent chat, voting, vote-locked, settings, error, and connection layers. `ScreenManager` loads configured assets, changes one primary screen at a time, keeps overlays separate, emits visual events, applies accessibility preferences, and performs a short fade. Navigation from `go-*` buttons resolves to a registered `ScreenId`.

## Install and preview

1. In Unity, create or select a GameObject with a `UIDocument`.
2. Choose **Thief & the Necklace → Visual → Install PV2 Screens On Selected UIDocument** to assign the screen and overlay UXML assets.
3. Choose **Thief & the Necklace → Visual → Create PV2 Visual Screen Lab Scene** to make `VisualScreenLab.unity` and a screen-sized PanelSettings asset. The command refuses to overwrite an existing lab scene and creates its scene additively.

The lab uses representative public sample labels so every page can be reviewed. Room forms validate room names and 5-character room codes before entering the lobby. `LobbyScreenController` reports ready/start actions to the owning runtime; bind a `LobbyScreenViewModel` to enable the start action only when the host says it is allowed. `BindVoteTargets` builds the voting options from public player data and omits the local player as a target. Subscribe to `VoteSubmitted`, then only move to Reveal when the authoritative game runtime authorizes that state. `AuthorizedRevealViewModel` is the only view model containing revealed role information.

## Runtime integration

Assign the selected scenario, private-player view, public player list, timer and result data through `BindScreen`, `BindLobby`, and `BindVoteTargets`. `RoomRequested`, `LobbyReadyChanged`, `LobbyStartRequested`, and `VoteSubmitted` are presentation intents that the application must validate and forward to its core services. They do not mutate game state by themselves. Screen and overlay transitions never determine roles, votes, scores, or outcomes.

The settings controls persist the project’s existing high-contrast, reduced-motion and text-scale preferences. Width changes toggle a compact layout class in C# because USS does not use browser-style media queries. Player seats can be positioned from the reusable `Visual.Gameplay.PlayerSeatLayout` algorithm.

## Scope note

PV2 provides the screen structure, navigation, input validation, visual states and runtime binding contracts. Final illustrations, network room services, scenario data wiring, authoritative gameplay transitions, and production QA still depend on the art and core runtime integration planned for later builds. The screen lab scene is generated by the Unity menu command; the source workspace may not contain the generated `.unity` file until that command is run.

The core should call ConfirmVoteLocked() only after accepting the vote, and should call Show(ScreenId.Reveal) with an AuthorizedRevealViewModel only when reveal is authorized. After round results, the next-round action returns to Scenario Intro; the runtime decides when Match Results is available.
